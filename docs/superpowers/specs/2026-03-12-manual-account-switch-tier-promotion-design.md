# 手动切号整层提升设计

## 背景

当前 Codex 账号池的“切到主组 / 切到备组”虽然使用的是主备层级语义，但后端实际执行时只会把被点击的单个账号抽出来并插入目标层。这样会把原本处于同一 `priority` 层的账号拆散，导致“手动切组”在体验上更像“只切单账号”，与用户对主组 / 备组的理解不一致。

同时，运行时缓存仍会记录手动选中的具体账号，所以现状其实混合了“层级切换”和“单账号置顶”两套语义，理解和维护成本都偏高。

## 目标

- 手动切到主组或备组时，按“同一优先级层”整体移动，不再拆散原有层级成员。
- 被点击的账号在手动切到任一层后，都作为该层内的当前活跃账号；只要调度落到该层，就优先命中它。
- 前后端对手动主备预览和实际执行保持一致，避免页面提示与真实结果不一致。

## 非目标

- 本次不引入新的持久化分组字段，如独立的 `group` 列或新的组表。
- 本次不改变层内自动排序规则；同层账号的利用率、健康度等排序逻辑保持现状。
- 本次不改变“切到主组 / 备组”的接口形态，仍沿用现有 `primary` / `backup` 语义。
- 本次不单独重做请求追踪页或其他页面的切换 UI；它们若复用相同后端语义，应被动获得一致结果，但不作为新增交互范围。

## 方案

### 手动主备重排

- 将 `MoveAccountToTier` 的重排单位从“单个账号”调整为“目标账号所在的整个 priority tier”。
- 整层移动按“共享同一 `priority` 的全部账号”处理，包含当前不可调度、disabled、cooldown 中的账号；手动主备只调整层级关系，不改变账号可调度状态。
- 处理流程：
  - 先按当前 `priority` 将账号分层。
  - 找到目标账号所属的原始层。
  - 将这一整层从原位置移除，再插入到目标层位置。
  - 重新按 `10, 20, 30...` 写回层级优先级，保持现有主备层编号规则。
- 这样点击某个主组账号切到主组时，如果它原本就在主组层，则数据库优先级可能不变化，但仍会刷新运行时活跃选择。

### 运行时活跃账号

- 保留当前“显式选中具体账号”的能力。
- 任何“有效的手动切换”一旦发生，都先失效旧的运行时选择和最近一次调度快照，避免继续沿用切换前的降级粘性与候选展示。
- 当目标层移动完成后：
  - 无论目标是主组还是备组，都把用户点击的账号写入该层运行时活跃选择；
  - 若本次是手动切到备组，则该层立即成为当前实际使用层。
- 这样下一次调度会基于新的手动选择优先落到该层并命中点击账号；若该账号失效，则仍按该层既有的自动排序规则回退到同层其他账号。

### 行为矩阵

| 场景 | `changed` | 清空旧运行时选择/快照 | 写入主组活跃账号 |
| --- | --- | --- | --- |
| 切到主组，层级顺序发生变化 | `true` | 是 | 是 |
| 切到主组，层级顺序未变，但切换了同层的活跃账号 | `true` | 是 | 是 |
| 切到主组，层级顺序未变，且当前活跃账号已经是目标账号 | `false` | 否 | 否 |
| 切到备组，层级顺序发生变化 | `true` | 是 | 是 |
| 切到备组，目标层已经是备组位置，但切换了该层当前账号 | `true` | 是 | 是 |
| 切到备组，目标层已经是备组位置，且当前账号已是目标账号 | `false` | 否 | 否 |
| 切到备组，但当前只有 1 个层级，无法形成独立备组 | `false` | 否 | 否 |

### 前端预览与提示

- 真实用户交互链路仍以 `useAccountPoolActions -> MoveUpstreamAccountToTier` 为主，Wails API 返回的 `changed` 语义必须与新的后端运行时语义保持一致。
- 前端纯函数 `buildManualFailoverPriorityPlan` 继续作为一致性 helper，改为按整层移动生成预览结果，而不是只抽出单个账号。
- 成功提示文案仍可保持“已将某账号切到主组/备组”。
  - 切到主组时，其实际含义是“该账号所在层已整体提升，且该账号成为该层当前活跃账号”；
  - 切到备组时，其实际含义是“该账号所在层已整体切到备组并立即接管，且该账号成为该层当前活跃账号”。
- 如有层级摘要展示，应继续以 `priority` 层为单位统计，不新增新的分组概念。

## 错误处理与边界

- 目标账号不存在时，仍返回“账号不存在”错误。
- 若当前没有任何可调整账号，仍返回现有错误。
- 若目标账号所在层已经位于目标层位置：
  - 不强制制造无意义的优先级更新；
  - 但当运行时当前活跃账号不是该账号时，仍视为一次有效手动切换。
- 若目标是备组但当前只有 1 个层级，视为无有效切换；前端可进一步将该操作禁用或展示为不可执行。
- 只有目标账号所在层整体不可识别时，才中止重排；同层内其他账号缺失或空指针应继续沿用当前容错方式跳过。

## 测试

- 后端单测补充：
  - 目标账号切到主组时，其原同层账号也一起提升到主组优先级。
  - 目标账号切到备组时，其原同层账号也一起下沉到备组优先级。
  - 原层已经在主组位置但点击了不同账号时，仍会刷新运行时活跃账号，并让 API 返回 `changed=true`。
  - 原层已经在备组位置但点击了不同账号时，仍会刷新运行时活跃账号，并让 API 返回 `changed=true`。
  - 任意有效手动切换后，旧运行时选择和最近一次调度快照都会失效；切到备组后，该层立即成为当前使用层，而不是继续沿用旧的 sticky tier/account。
  - 当前只有 1 个层级时，切到备组返回 `changed=false`，且不会误清空快照或写入新的运行时选择。
  - 整层提升后，下一次调度优先命中被点击账号；若其不可调度，则在同层内按现有排序选择其他账号。
- 前端测试或等价验证补充：
  - `useAccountPoolActions` 调用链在 `changed=true` 时仍走成功提示和快照刷新分支。
  - 本地预览得到的优先级变化与后端重排结果一致。

## 验收标准

- 手动切某个账号到主组后，该账号原本同 `priority` 的账号必须与其一起成为主组层。
- 手动切某个账号到备组后，该账号原本同 `priority` 的账号必须与其一起成为备组层。
- 任何有效手动切换后，旧的运行时选择与最近一次调度快照都必须立即失效。
- 手动切到主组成功后，下一次 `/v1/responses` 在该账号可调度时必须优先命中它。
- 手动切到备组成功后，该层必须立即成为当前实际使用层，并优先命中该账号。
- 当前只有 1 个层级时，切到备组必须返回 `changed=false`。
- 当数据库 `priority` 未变化但主组或备组点击切换了层内活跃账号时，`MoveUpstreamAccountToTierResult.changed` 仍必须为 `true`。
- 前端手动主备预览结果与后端真实持久化结果一致。
