# 账号池大规模管理页面设计

## 背景

当前 Codex 账号池页面更偏向“小规模人工运营”：

1. 主视图仍是单个长列表，顶部顺序串联统计卡片、最近一次调度结果和账号列表。
2. 每一行同时承载启停、状态、主备切换、额度、倍率、刷新时间与多个操作按钮，账号数量较少时可读，但数量继续增长后会迅速失去扫描效率。
3. “账号资产管理”“主备编排”“异常处理”“最近一次调度观察”混在同一页，导致用户在不同任务之间频繁切换心智。
4. 前台交互高度依赖 `priority` 数字。随着账号规模扩大，纯数字优先级虽然便于后端排序，但并不适合前端日常运营心智。

在账号数增长到 `80 ~ 200` 时，页面的主要瓶颈不再是“能不能展示所有信息”，而是：

1. 能不能快速定位目标账号。
2. 能不能优先找到真正影响调度的问题账号。
3. 能不能批量完成保养与修复动作。
4. 能不能把“资产管理”和“调度编排”分开，避免相互抢占空间。

## 目标

本轮页面改造以“路线 B：账号资产 + 调度编排双视图”为核心，目标如下：

1. 将账号池页面重构为面向 `80 ~ 200` 个账号的后台管理体验。
2. 把“账号资产管理”“调度编排”“异常中心”拆分为独立职责区域，降低单页认知负担。
3. 把主界面的管理语言从“纯 `priority` 数字”调整为“`主组 / 备组 / 冷备 + 组内顺序`”。
4. 让主列表回到高密度扫描模式，把重信息和高风险动作收敛到右侧详情抽屉。
5. 提供保存视图、批量操作和预置异常队列，支持持续增长的账号规模。
6. 将“最近一次调度结果”收敛为调度编排页的一部分，而不是持续占用首页主视图。

## 非目标

本轮设计不包含以下内容：

1. 不改动账号池后端调度核心语义，仍保留现有基于 `priority` 的分层与降级逻辑。
2. 不引入新的复杂权限系统、协作审批流或多租户隔离方案。
3. 不在本轮就支持任意自定义分组；前台先固定为 `主组 / 备组 / 冷备`。
4. 不重做 OAuth 授权流程、倍率字段语义或 quota 采集逻辑。
5. 不在主列表直接展示所有调度解释明细；完整候选决策仍作为按需查看信息。

## 用户任务与设计原则

### 核心任务

账号规模扩大后，用户的高频任务可以归纳为四类：

1. 找某个账号并快速查看其状态、额度和最近错误。
2. 处理一批存在相同问题的账号，例如鉴权失效、额度将尽、长时间未刷新。
3. 调整主组 / 备组 / 冷备关系，确认当前调度实际落点。
4. 在出现降级或不可用时，快速判断问题是否影响主组，并执行切换或修复。

### 设计原则

围绕这些任务，页面遵循以下原则：

1. 资产管理与调度编排必须分离。
2. 主列表只负责扫描，不负责承载全部细节。
3. 重信息、编辑和高风险动作放进右侧抽屉。
4. 异常中心必须像问题队列，而不是第二个完整账号列表。
5. 调度编排页看“组的运行态”，而不是再看一遍所有账号。

## 信息架构

页面重构后采用四块结构：

1. `概览`
2. `账号资产`
3. `调度编排`
4. `异常中心`

### 1. 概览

`概览` 只承担轻量总览职责，不承担主要操作。

建议展示：

1. 账号总数
2. 可用账号数
3. 鉴权失效账号数
4. 主组风险概览
5. 最近一次调度的摘要入口

设计意图：

1. 让用户在进入页面后快速了解整体健康度。
2. 不把概览做成第二个操作台，避免页面职责扩散。

### 2. 账号资产

`账号资产` 是主工作台，负责：

1. 搜索账号
2. 多条件筛选
3. 保存视图
4. 批量治理
5. 打开右侧抽屉查看详情并执行单账号操作

这是日常使用频率最高的页面，应优先优化“扫描速度”和“定位效率”。

### 3. 调度编排

`调度编排` 负责展示和调整：

1. `主组`
2. `备组`
3. `冷备`

同时在页面底部展示“最近一次调度结果”的紧凑时间线与入口摘要。

设计意图：

1. 把用户从“翻全量账号表找主备关系”中解放出来。
2. 让调度编排页聚焦“组关系”和“当前运行态”，而非资产盘点。

### 4. 异常中心

`异常中心` 是问题处理工作台，不是第二个资产表。

它的职责是：

1. 汇总真正需要优先处理的账号问题。
2. 默认按“是否影响调度”排序。
3. 提供批量测试、批量刷新画像、批量启停、批量移组等动作。

建议分为两个区：

1. `救火`
2. `保养`

其中：

1. `救火` 关注已经影响或即将影响调度的问题。
2. `保养` 关注长期未刷新、长期未成功等维护类提醒。

## 分组与心智模型

### 前台分组模型

前台交互固定使用三组：

1. `主组`
2. `备组`
3. `冷备`

并支持“组内顺序”概念。

### 后台兼容原则

虽然前台心智改为组模型，但后端仍可继续使用现有 `priority` 进行持久化与排序。前台只需满足以下映射原则：

1. 用户在主界面优先看到的是组别和组内顺序，而非裸露的 `priority` 数字。
2. `priority` 仍保留在高级信息中，便于调试、排障与兼容旧逻辑。
3. 前端所有“提升为主组 / 下放到备组 / 提升到冷备”动作，本质上仍映射到现有层级调整机制。

这样可以在不打断现有调度模型的前提下，降低前台理解成本。

## 账号资产页设计

### 1. 页面目标

`账号资产` 页的目标不是展示“尽可能多的信息”，而是：

1. 让用户在几秒内找到想找的账号。
2. 让用户快速判断这批账号是否健康。
3. 让用户在不离开主页面的情况下完成大多数单账号处理。

### 2. 页面布局

页面自上而下分为四层：

1. 搜索与主操作区
2. 筛选条与保存视图
3. 高密度资产表格
4. 仅在多选时出现的批量操作条

点表格行后，右侧弹出详情抽屉。

### 3. 主表格字段

主表格建议使用以下字段：

1. `选择`
2. `账号名`
3. `授权方式`
4. `计划类型`
5. `组别`
6. `运行状态`
7. `5h`
8. `d7`
9. `最近成功`
10. `最近刷新`
11. `操作`

字段取舍原则：

1. `priority` 不再占据主表格固定列，收敛到抽屉中的“路由配置”区域。
2. `倍率` 默认不进主表格；它是重要信息，但不是高频扫描信息。
3. `Base URL`、`备注`、`负责人` 等元数据默认不占主列，但必须支持被搜索命中。
4. `5h` 与 `d7` 保留为摘要态，完整 reset 信息放进抽屉。

### 4. 搜索与筛选

建议顶部搜索框支持以下内容：

1. 账号名
2. 备注
3. 标签
4. `Base URL`

筛选条建议支持：

1. 授权方式
2. 计划类型
3. 组别
4. 运行状态
5. 风险状态
6. 排序方式

### 5. 保存视图

保存视图是中大规模账号管理的关键能力，第一版建议支持常用视图，例如：

1. `主组异常`
2. `待处理 OAuth`
3. `额度风险`
4. `冷备 free 账号`

设计意图：

1. 减少重复配置筛选器的成本。
2. 让日常巡检和保养更像“打开预设工作台”。

### 6. 行级交互规则

为避免回到“每行塞满动作”的旧模式，主表格行只负责轻操作和打开抽屉：

1. 点击整行：打开右侧详情抽屉。
2. 行内保留的轻操作：
   - 启用 / 停用
   - `更多` 菜单

不建议继续把以下动作都平铺在每一行：

1. 编辑
2. 刷新画像
3. 测试连通性
4. 设为主组
5. 设为备组
6. 删除

这些动作统一收敛到抽屉或批量操作条。

### 7. 右侧详情抽屉

详情抽屉是单账号处理工作区，建议包含五个区块：

1. `概览`
   - 账号名
   - 授权方式
   - 计划类型
   - 组别
   - 运行状态
2. `额度`
   - `5h`
   - `d7`
   - reset 时间
   - quota 状态
3. `健康`
   - 最近成功
   - 最近刷新
   - 最近错误
   - 最近测试结果
4. `路由配置`
   - 当前组别
   - 组内顺序
   - `Base URL`
   - 倍率
   - 原始 `priority`
5. `动作`
   - 测试
   - 刷新画像
   - 编辑
   - 移组
   - 删除

抽屉的主要收益：

1. 保持主表格高密度。
2. 提供完整上下文，避免为了处理一个账号跳转多个弹窗。
3. 把高风险操作集中到更有上下文的环境里。

## 批量治理设计

### 1. 出现条件

当用户在资产表或异常中心选择多条账号时，底部批量操作条出现。

### 2. 第一版批量能力

第一版建议仅提供价值最高、语义最清晰的四种批量操作：

1. `批量测试`
2. `批量刷新画像`
3. `批量启用 / 停用`
4. `批量移到备组 / 冷备`

### 3. 设计边界

本轮不建议引入“批量编辑全部字段”，原因如下：

1. 语义不清晰，容易误改。
2. 风险高，回滚与提示成本大。
3. 会显著拉高第一版交互复杂度。

### 4. 批量反馈

每次批量操作前后都应明确提示影响范围，例如：

1. `将 8 个账号移到备组`
2. `批量刷新 12 个账号画像`

这样更符合中大规模治理场景下的可确认性。

## 调度编排页设计

### 1. 页面目标

`调度编排` 页的目标是帮助用户理解并调整：

1. 当前哪个组在承担主要流量。
2. 当前活跃账号是谁。
3. 是否已发生降级。
4. 主组、备组、冷备的候选关系是否合理。

### 2. 页面结构

页面建议分为两层：

1. 顶部：当前运行态摘要
2. 中部：`主组 / 备组 / 冷备` 三组卡片
3. 底部：最近一次调度结果时间线

### 3. 组卡片内容

每个组卡片只展示与编排强相关的信息：

1. 当前活跃账号
2. 组内前几名候选
3. 该组健康摘要
4. 组动作

设计上不再展示完整资产字段，避免变成“又一张账号表”。

### 4. 支持的编排动作

第一版只支持语义明确的组动作：

1. `提升为主组`
2. `下放到备组`
3. `提升到备组`
4. `组内顺序调整`
5. `指定当前活跃账号`

详细编辑仍然回到资产页抽屉完成。

### 5. 最近一次调度结果

最近一次调度结果不再作为首页的大卡片长期占位，而是收敛到调度编排页底部。

展示策略：

1. 默认只展示一条时间线式摘要：
   - 最近命中账号
   - 命中组别
   - 是否降级
   - 最终错误摘要
2. 按需展开查看完整候选决策说明。

这样既保留可观测性，又避免持续挤占主视图空间。

## 异常中心设计

### 1. 页面目标

异常中心负责让用户优先处理真正值得现在处理的问题。

### 2. 页面分层

建议分为两个区：

1. `救火`
2. `保养`

含义如下：

1. `救火`：已经影响或即将影响调度的异常。
2. `保养`：暂不影响调度，但长期看需要维护的异常。

### 3. 预置异常队列

第一版建议提供以下预置队列：

1. `鉴权失效`
2. `主组风险`
3. `额度将尽`
4. `已耗尽待重置`
5. `最近测试失败`
6. `长时间未成功`
7. `长时间未刷新`

这些队列应默认可直接进入，而不是让用户从空白筛选器开始配置。

### 4. 排序策略

异常中心默认按以下顺序排序：

1. 是否影响调度
2. 所在组别
3. 最近成功时间

这样可以把真正紧急的问题自动推到最前。

### 5. 与抽屉的关系

异常中心中的单行记录仍然可以打开同一个详情抽屉，保持操作一致性。

## 状态体系

随着账号数增长，前端状态展示必须从“堆 badge”改成“状态分层”。

### 1. 运行状态

用于主表格和组卡片的基础状态：

1. `可用`
2. `冷却中`
3. `鉴权失效`
4. `已停用`

### 2. 额度状态

用于概括 quota 风险：

1. `正常`
2. `紧张`
3. `已耗尽`
4. `无限额`
5. `未刷新`

### 3. 风险等级

用于异常中心：

1. `P1`
   - 已影响主组或当前调度
2. `P2`
   - 短时间内可能影响调度
3. `P3`
   - 保养类提醒

### 4. 展示规则

建议遵循：

1. 主表格主要展示运行状态和额度状态。
2. 异常中心主要使用风险等级组织队列。
3. 原始后端状态和细粒度说明进入抽屉展示。

## 元数据扩展建议

为了支持规模化管理，建议为后续版本预留以下元数据能力：

1. 标签
2. 负责人
3. 备注
4. 环境 / 用途

这些字段不要求第一版在主表格中全部展示，但应在搜索、筛选与抽屉中可见，逐步演进为真正的“账号资产”管理能力。

## 典型操作流

### 1. 日常巡检

1. 进入 `异常中心`
2. 查看 `救火` 队列中的 `P1 / P2`
3. 打开右侧抽屉查看详细原因
4. 在抽屉内执行测试、刷新、启停或移组

### 2. 查找某个账号

1. 进入 `账号资产`
2. 使用搜索或保存视图定位账号
3. 点击行打开抽屉
4. 在抽屉中查看详情或执行操作

### 3. 调整主备关系

1. 进入 `调度编排`
2. 查看主组 / 备组 / 冷备当前运行态
3. 执行组间提升、下放或组内活跃账号切换
4. 在页面底部查看最近一次调度结果确认是否恢复

### 4. 批量保养

1. 在 `账号资产` 或 `异常中心` 通过视图和筛选选中一批账号
2. 触发批量测试、批量刷新画像或批量移组
3. 根据结果继续复核异常队列

## 风险与权衡

### 1. 页面数量增加

从单页改为多职责页面会引入更多导航层级，但收益是：

1. 每个页面职责更清晰。
2. 单页信息密度更可控。
3. 账号规模增长后不需要继续向一个列表堆更多内容。

### 2. 前台心智与后端模型不完全一致

前台改为“组 + 顺序”后，用户不再直接围绕 `priority` 操作。需要在抽屉中保留原始 `priority` 及必要解释，避免高级排障场景失去透明度。

### 3. 批量能力需要明确反馈

批量治理是规模化管理的关键，但也提高了误操作风险。因此操作前后的影响提示、结果反馈和失败明细需要在实现阶段重点补齐。

## 验收标准

当以下条件满足时，可认为这版设计达成目标：

1. 页面职责被拆分为 `概览 / 账号资产 / 调度编排 / 异常中心` 四块，且边界清晰。
2. 主工作台为 `账号资产`，支持搜索、筛选、保存视图和批量操作。
3. 主表格不再承载过多行级动作；详情与高风险操作收敛到右侧抽屉。
4. `调度编排` 页以 `主组 / 备组 / 冷备` 为主心智，最近一次调度结果位于其底部。
5. `异常中心` 以问题队列方式组织异常，并默认按是否影响调度排序。
6. 前台主要管理语言变为“组别 + 组内顺序”，`priority` 退居高级信息层。
7. 页面在账号数量增长到 `80 ~ 200` 时，仍能维持较高的扫描效率和可管理性。
