# 启动异步连通性检查设计

## 背景

近期系统已经把“健康检查”收敛为“手动/批量连通性测试”，默认不再在启动阶段自动探测端点。这样避免了无谓轮询，但也带来一个体验问题：应用刚启动后，端点列表和 Codex 账号列表往往仍处于“未检测”或旧状态，用户需要手动触发一次连通性测试才能看到当前可达性。

本次设计在不回退到后台定时轮询的前提下，为应用启动过程补充一轮一次性的异步连通性检查。它必须满足两个条件：

1. 不阻塞 Wails 应用启动，不影响代理服务可用速度。
2. 只更新最近连通性状态、日志和前端展示，不直接改变运行时调度决策。

## 目标

- 在应用启动完成后，若存在 `cc` 端点或 `codex` 账号，则异步触发一轮启动连通性检查。
- 端点侧复用现有连通性检查逻辑，更新 `Healthy`、`LastCheck`、`ResponseTime` 等状态。
- 账号侧复用现有 `TestUpstreamAccount` 逻辑，写回 `last_success_at`，并保留 OAuth 画像刷新等既有副作用。
- 启动检查失败只进入日志和界面状态，不触发冷却、禁用、切换账号或端点。

## 非目标

- 不恢复后台定时探测。
- 不因为启动检查结果主动修改账号池调度状态、冷却状态或手动选中状态。
- 不新增用户可配置项；本次先采用固定并发和现有超时配置。

## 方案概览

### 触发时机

在 `App.startup()` 主流程末尾、代理服务与事件桥接已完成后，异步拉起一轮启动连通性检查。`startup` 本身只负责调度 goroutine，不等待检查完成。

### 端点检查

端点侧直接复用 `endpoint.Manager.BatchHealthCheckAll()`：

- 若当前没有任何端点，则跳过。
- 若存在端点，则在独立 goroutine 中触发批量连通性测试。
- 继续沿用现有并发限制、状态写回与前端刷新回调。

### 账号检查

账号侧新增一个仅用于启动阶段的批量检查入口：

- 从账号池中读取账号列表。
- 仅保留 `enabled=true` 且存在凭据的账号。
- 使用小并发池逐个调用现有 `TestUpstreamAccount(ctx, id)`。
- 单个账号失败只记录日志，不中断整个批量任务。
- 批量任务结束后触发一次账号列表刷新事件，便于前端看到最新 `last_success_at` 和画像信息。

建议默认并发上限为 `4`，避免应用刚启动时对上游同时发起过多请求。

## 数据流

1. `App.startup()` 完成核心初始化。
2. `App` 通过 fire-and-forget 方式启动“启动连通性检查”编排器。
3. 编排器分别判断端点和账号是否需要检测。
4. 端点任务调用现有 `BatchHealthCheckAll()`，账号任务调用新的批量启动检查入口。
5. 检查过程中的成功/失败结果写回各自现有状态字段。
6. 检查完成后通过既有事件推送刷新前端展示。

## 错误处理与日志

- 启动检查中的任何错误都不得上抛为启动失败。
- 日志应带统一前缀，例如“启动连通性检查”，用于区分用户手动点击触发的连通性测试。
- 单个账号失败需要记录账号 ID / 名称和错误摘要，便于排查。
- 若任务因无端点或无可测账号而跳过，应输出轻量级 debug/info 日志，避免误判为未执行。

## 代码边界

建议按以下职责拆分：

- `app.go`
  - 只保留启动时机接线，在 `startup` 末尾调用启动检查调度方法。
- `app_startup_connectivity.go`
  - 承载启动检查编排逻辑，避免 `app.go` 继续膨胀。
- `internal/service/account_pool_startup_connectivity.go`
  - 承载账号池启动检查批处理逻辑，复用现有 `TestUpstreamAccount`。
- `internal/service/account_pool_startup_connectivity_test.go`
  - 覆盖筛选、并发与错误隔离行为。
- `app_startup_connectivity_test.go`
  - 覆盖“无配置时跳过”和“启动流程不等待检查完成”的编排语义。

## 测试策略

- 为 `App` 编排逻辑补单测，验证：
  - 无端点且无账号时不会触发任何任务。
  - 启动流程只调度异步任务，不等待网络完成。
- 为账号池批量启动检查补单测，验证：
  - 只检查启用且有凭据的账号。
  - 单个账号失败不会阻断其他账号。
  - 返回摘要统计可用于日志。
- 回归现有端点测试，确保 `Manager.Start()` 仍不自动做同步检查，避免语义倒退。

## 结论

采用“在 `App.startup()` 末尾异步触发一次性检查”的方案，既能补足启动后的状态感知，也不会回退到高成本的后台轮询。端点侧最大化复用现有能力，账号侧新增一个轻量批处理入口，整体风险较低、边界清晰。
